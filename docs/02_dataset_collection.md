# Сбор и подготовка датасета

Сборка **FPB + MyFoodRepo v2.1** выполняется в [ноутбуке 02](../notebooks/02_prepare_dataset.ipynb). Цель этапа — получить единый датасет для детекции и классификации объектов еды в формате YOLO.

1. **Получение исходных данных.** FPB скачивается с сохранением версии источника. MyFoodRepo распаковывается из локальных архивов train и valid при `MYFOODREPO_SOURCE = "archives"`. В режиме `"download"` train загружается с закреплённого зеркала, valid используется из локального архива. Прогресс загрузки, распаковки и сборки отображается через tqdm.
2. **Приведение разметки.** Из FPB сохраняются класс и рамка, поле массы отбрасывается. Для MyFoodRepo рамки вычисляются по полигонам сегментации. Объекты записываются как `class_id x_center y_center width height` с нормализованными координатами.
3. **Объединение классов.** Применяются проверенные соответствия из ноутбука 01: 44 пары объединяются, `pancake` и `bliny` остаются раздельными. Итоговый словарь содержит 417 классов;
4. **Сохранение разбиений.** Авторские train/val FPB и train/valid MyFoodRepo сохраняются; valid переводится в YOLO-раздел `val`. Случайное переразбиение MyFoodRepo train не выполняется. FPB test без открытых меток хранится отдельно от размеченных выборок.
5. **Очистка и проверка.** Проверяются размеры изображений, классы и координаты рамок. Из разметки MyFoodRepo убираются вырожденные компоненты полигонов и повторные записи одного объекта. На этапе сборки исключаются дубликаты изображений и конфликты разметки; подробные правила приведены ниже. Сохранённые изображения и YOLO-метки повторно читаются и выводятся с рамками для визуальной проверки.
6. **Сохранение результата.** Исходные изображения находятся в `data/raw/`, кеш и сведения об источниках — в `data/metadata/`. Готовые сборки сохраняются отдельно в `data/processed/fpb_myfoodrepo_preview/` и `fpb_myfoodrepo_full/`: изображения, метки, конфигурация YOLO, списки выборок, соответствия классов и manifest. Причины исключения записей сохраняются только при наличии исключений.

Сначала используется `preview` для проверки пайплайна, затем `full` для подготовки всех данных. При `OVERWRITE = False` готовая сборка переиспользуется; для её замены задаётся `True`. Завершённая распаковка также кешируется. Food-101 в обучающую сборку не входит и может использоваться отдельно для просмотра предсказаний модели.

## Что удаляется при очистке разметки MyFoodRepo

Очистка применяется к данным при импорте и экспорте. **Исходные архивы, COCO JSON и фотографии в `data/raw/` не удаляются и не переписываются.** Удаление компонента полигона, удаление повторной аннотации и исключение изображения из итоговой сборки — разные операции.

### Вырожденные компоненты — `degenerate_polygon_components`

Сегментация одного объекта может состоять из нескольких полигонов. Для замкнутого контура требуется не менее трёх точек — шести значений `[x1, y1, x2, y2, x3, y3, ...]`. Компоненты с меньшим числом точек отбрасываются: отдельная точка или отрезок не описывают область объекта.

**Сохраняются сам объект, его класс и все оставшиеся пригодные полигоны.** Рамка пересчитывается по минимальным и максимальным координатам этих полигонов. Лишние точки больше не могут растянуть её на посторонние области фотографии. Проверяется именно число точек; маленький размер объекта сам по себе не является основанием для удаления.

Примеры из train:

| `image_id` / `annotation_id` | Класс | Что удаляется | Что сохраняется |
| --- | --- | --- | --- |
| `160651` / `267245` | `feta` | Отдельная точка далеко от двух контуров сыра | Оба контура и одна аннотация объекта |
| `105317` / `151299` | `red_cabbage_raw` | Дополнительный компонент из двух точек | Основной контур и аннотация объекта |

Если после фильтрации не остаётся ни одного пригодного полигона, импорт останавливается с ошибкой. Аннотация не пропускается молча. Нечётное число координат, нечисловые/нефинитные значения, недопустимая рамка или выход координат оставшихся полигонов за границы изображения также требуют исправления и останавливают импорт.

### Повторные аннотации — `duplicate_object`

Внутри **одной фотографии** сравниваются исходный `category_id` и полный список координат полигонов после удаления вырожденных компонентов. Если они полностью совпадают, первая запись сохраняется, а последующие исключаются. Различие `annotation_id` не делает такие записи разными объектами. Это предотвращает появление нескольких одинаковых YOLO-меток для одного объекта.

| `image_id` | Класс | Исходные `annotation_id` | Результат |
| --- | --- | --- | --- |
| `136359` | `bread` | `192278`, `192279` | Сохраняется `192278`, удаляется повтор `192279` |
| `8235` | `water` | `2750`, `2751`, `2752`, `2801` | Сохраняется `2750`, удаляются три повтора |

Несколько объектов одного класса на фото сохраняются, если их полигоны различаются. Близкие рамки, одинаковые названия классов и визуальное сходство сами по себе не приводят к удалению. На этом этапе сравниваются полигоны, а не только охватывающие их рамки.

Одна исходная аннотация может получить обе причины: сначала из неё удаляется вырожденный компонент, затем оставшаяся разметка оказывается повтором ранее прочитанного объекта. Поэтому число записей аудита не всегда равно числу удалённых объектов.

## Какие изображения исключаются из итоговой сборки

После объединения классов выполняется отдельная проверка фотографий FPB и MyFoodRepo. Исключённые изображения и их метки не включаются в `processed/`; исходные файлы остаются на месте.

| Причина | Условие | Действие |
| --- | --- | --- |
| `pixel_duplicate` | Совпадают размеры и SHA-256 декодированных RGB-пикселей, противоречий в разметке нет | Сохраняется одна запись, остальные исключаются вместе с их метками |
| `conflicting_duplicate` | У одинаковых по пикселям изображений различаются наборы итоговых классов или координат рамок | Исключается вся группа конфликтующих копий; правильная разметка автоматически не выбирается |

Сначала сохраняется запись **с разметкой**: если копия есть в неразмеченном test и в размеченной выборке, удаляется копия без разметки. Среди размеченных записей приоритет: `test` → `val` → `train`; при равенстве используются источник и исходный ID. Например, при одинаковых размеченных фото в train и val сохраняется val. При сравнении разметки используются итоговые ID классов и координаты рамок с округлением до восьми знаков; порядок объектов значения не имеет.

Это проверка точных копий: похожие фотографии, другие ракурсы и изменённые по размеру изображения автоматически не удаляются. Поле `group_id` остаётся служебной информацией: его совпадение между train/val/test не исключает записи и не считается ошибкой проверки. Совпадение частей имени файла также не является основанием для удаления.

После изменения правил очистки готовые сборки необходимо пересобрать с `OVERWRITE = True`. Версия пайплайна в подписи кеша изменена, поэтому сборка с прежней фильтрацией не будет автоматически переиспользована. Исходные файлы при пересборке используются повторно.
